# AGENTS.md

## Назначение и контекст

Инструкции для AI-агентов в репозитории `aechat-links`. Главная цель: вносить минимальные безопасные изменения строго в рамках запроса пользователя. Язык по умолчанию: русский.

## Принципы коммуникации

1. Краткость и фокус: суть решения, измененные файлы, проверки, ограничения.
2. Исключение шума: не пересказывать очевидное, не дублировать риски, избегать пространных вводных фраз.
3. Промежуточные сообщения: выводить только для статуса, критических находок, рисков или согласования плана.
4. Градация ответов: для простых задач — лаконичный итоговый список; для комплексных — сначала компактный план, затем работа строго по согласованному объему.

## Рабочий порядок и безопасность

1. Иерархия приоритетов: Прямой запрос пользователя > `AGENTS.md` > локальные комментарии в файлах.
2. Подготовка: до правок изучить архитектуру целевых файлов и свериться с `docs`. Учитывать контекст текущих изменений.
3. Точечное исследование: предпочитать `grep_search` и срезы `view_file` (до 150 строк) полному чтению объемных файлов для сохранения точности контекста.
4. Прозрачность: перед значимыми правками обязательно выводить `git status --short` и список целевых файлов.
5. Согласование: при неоднозначных решениях предложить 2–3 варианта с компромиссами (trade-offs). Не расширять согласованный объем работ без явного подтверждения.
6. Контроль внешних правок: при обнаружении сторонних изменений в целевых файлах или действиях пользователя параллельно остановить правки и запросить инструкции.
7. Безопасность и откат: рискованные изменения сопровождать планом отката. Вести историю действий для последующего разбиения на атомарные коммиты.
8. Статическая валидация: перед завершением проверить импорты, типы, относительные пути, ссылки и якоря.

## Ограничения на команды

1. Запрещено без явного запроса запускать ресурсоемкие команды: `build`, `dev`, `test`, `lint`, `format`, `install`.
2. Запрещено без явного запроса выполнять сетевые команды и устанавливать пакеты.
3. Запуск комплексного форматирования `yarn format` (`tsc + stylelint + eslint + prettier`) и скрипта удаления пустых строк `node scripts/maintenance/removeEmptyLines.js <file>` выполнять строго по прямому запросу.

## Архитектура и структура проекта

1. Статьи размещаются в каталоге `src/pages/sections`.
2. Основные разделы статей: `aefaq`, `prfaq`, `psfaq`.
3. Каталоги исходного кода:
   - `src/components/content` — компоненты контента статей;
   - `src/components/features` — интерактивные инструменты и калькуляторы;
   - `src/components/layout` — каркас (шапка, футер, переходы);
   - `src/hooks` — пользовательские React-хуки;
   - `src/utils` — вспомогательные утилиты;
   - `src/styles` — SCSS-слои и модули.
4. Запрещено произвольно менять структуру каталогов `src/pages/sections/*` и имена файлов без согласования.

## Правила написания кода

1. Минимальная достаточность: изменять только то, что необходимо для решения задачи.
2. Запрет спекуляций: не выполнять попутный рефакторинг, косметические правки и перестановку кода.
3. Защищенные зоны: запрещено трогать `dist`, `node_modules`, автогенерируемые файлы, `.env*`, секреты и lock-файлы без прямого указания.
4. Стабильность контрактов: не менять публичные API, сигнатуры, контракты и внешнее поведение компонентов без согласования. Не менять смысловое содержание статей при выполнении технических задач.
5. Организация кода:
   - Запрещено использовать `index.ts`/`index.tsx` как реэкспорт или точку входа.
   - Разделять UI, бизнес-логику, алгоритмы, эффекты и низкоуровневые утилиты.
   - Если файл перегружен, выделять независимые части в `components`, `hooks`, `utilities` или `config`.
   - Повторяющуюся логику выносить в общие утилиты без изменения логики работы.
   - Использовать паттерн Early Exit (ранний возврат / guard clauses) вместо глубокой вложенности `if-else`.
6. Перемещение файлов: использовать исключительно `git mv`. При невозможности — запросить подтверждение на ручной перенос.
7. Качество и линтеры:
   - Строго следовать правилам ESLint, SonarJS, Stylelint. Запрещено обходить правила через `eslint-disable` или глобальные отключения.
   - Предупреждения линтеров устранять структурно (мемоизация компонентов, вынос булевых флагов в константы).
   - В хуках `useEffect` при добавлении таймеров, дебаунсов, событийных слушателей (scroll/resize) или подписок обязательно реализовывать очистку в функции возврата.
8. Стилизация: в SCSS-модулях (`*.module.scss`) избегать переопределений через `:global`. Все стили должны оставаться локальными.

## Соглашения об именовании

1. React-компоненты и файлы `.tsx`: `PascalCase`.
2. Утилиты, хуки и файлы `.ts`: `camelCase`.
3. Переменные и функции: `camelCase`; логические флаги начинаются с `is`, `has`, `can`, `should`.
4. Типы, интерфейсы и перечисления (enum): `PascalCase`.
5. Константы верхнего уровня: `UPPER_SNAKE_CASE`.
6. Интерфейсы пропсов компонентов: суффикс `Properties` (например, `ButtonProperties`).
7. Общие правила: не использовать транслит и неочевидные сокращения. CSS/SCSS-классы оформлять в стиле текущего файла.

## Стандарты документации

1. Документация в `docs/` — первичный источник проектных правил перед правками.
2. При изменениях, затрагивающих поведение, архитектуру или договоренности, синхронно обновлять или создавать статьи в `docs/`. При изменении `docs` или конфигов проверять актуальность `AGENTS.md`.
3. В русскоязычных заголовках писать с заглавной буквы только первое слово и имена собственные.
4. Стиль `docs/`: строго сплошное связное повествование на русском языке. Запрещены маркированные и нумерованные списки в текстовых описаниях (допускаются только в примерах кода). Текст делить на короткие логические абзацы по 2–4 предложения, разделенные пустой строкой.
5. Перекрестные ссылки: обязательно проставлять ссылки на связанные документы и исходные файлы.
6. При расхождении `docs` с кодовой базой сначала сообщить о несоответствии, затем предложить точечное исправление.

## Оформление контента и ссылок

1. Корневой контейнер статьи `src/pages/sections/**`: `<div className="article-content">`.
2. Структура вопроса: один вопрос — один компонент `DetailsSummary` с кратким заголовком `title` и стабильным латинским якорем `anchor` в `kebab-case`.
3. Переиспользование: при повторении ответа ссылаться на существующий якорь, а не копировать текст.
4. Готовые компоненты: проверять наличие `Addition`, `ArticleMedia`, `CodeSnippet`, `ContentFilter`, `NestedDetailsSummary`, `HostsAdobe`.
5. Текстовые ссылки: ссылки в тексте не должны быть длинными (кроме ссылок-вопросов). Для конструкций вида «по этой ссылке» тегом `<a>` оборачивать только слово «этой».
6. Типология статей FAQ:
   - Ошибки и сбои (`*Errors`, `*InstallProblems`): ноль вводных фраз; структура: симптом/ошибка → точная причина (1–2 предложения) → пошаговое решение → альтернатива.
   - How-To и инструменты (`*Actions`, `*Import`, `*Export`): прямой тезис о задаче и инструментах (встроенные vs плагины) без разгонных преамбул.
   - Гайды и матчасть (`*FromNewbies`, `*Performance`, `*Interface`): тезис/принцип работы → практическое применение → спокойный тон наставника-практика.
7. Тон и авторский голос: базово уважительный объясняющий стиль с обращением строго на «вы» без сухого бюрократизма. Обязательно сохраняются живые авторские реплики, ирония, образные обороты («в кои-то веки», «танцы с бубном», «палки в колёса», «грабли») и точечное первое лицо («я рекомендую», «в моей практике») для передачи реального опыта. Категорически запрещено выхолащивать тексты в сухие машинные конспекты или искусственные математические формулы: повествование должно оставаться естественным и связным.
8. Анти-паттерны и маркеры сгенерированного текста:
   - Запрещены разгоны мысли вслух («Прежде чем начать...», «Для начала нужно разобраться...», «Когда вы создаёте, то для того, чтобы появилось — нужно...»). Действует «правило первого предложения»: мысленный разгонный черновик отсекается, ответ начинается сразу с сути.
   - Полный запрет блогерских анонсов («В этой статье мы подробно разберём...», «В этой статье мы расскажем...», «В этой статье собрана подборка...»). В спойлере базы знаний читателю не нужны анонсы того, что он уже читает.
   - Устранение синтаксических петель и плеоназмов: тяжелые нагромождения союзов («для того, чтобы... то нужно...») упрощаются в пользу прямого и ясного строя предложений.
   - Запрещены псевдо-аналитические связки и поучения («Стоит отметить», «Важно подчеркнуть», «Необходимо помнить», «Нельзя не упомянуть»).
   - Запрещены искусственные выводы-эпилоги («Подводя итог...», «В заключение...»).
   - Запрещены шаблонная симметрия («не только..., но и...», навязчивые тройные перечисления).
   - Запрещены псевдо-глоссарии и списковые «суммаризации» по шаблону «два слова: пояснение к нему»: искусственное нарезание связной мысли на механические пункты с двоеточиями разрушает контекст. Списки используются исключительно для пошаговых инструкций и выбора вариантов, а объяснения излагаются естественным текстом.
   - Запрещены абстрактные оценки без фактуры («высокая эффективность», «колоссальный прирост») вместо точных параметров кодеков, версий и цифр.
   - Запрещены круглые скобки для пояснений и перечислений: скобки разрывают ритм чтения и прячут суть. Важные пояснения, форматы файлов или примеры формулируются прямо в тексте через тире, союзы или запятые. Если мысль второстепенна — она удаляется. Круглые скобки допустимы исключительно для обозначения года в версиях программ (например, `25.2 (2025)`), синтаксиса кода (вызовы функций вроде `loopOut()`, индексы массивов) и шорткатов.
   - Запрещены отчужденные неопределенно-личные формы третьего лица множественного числа («используют», «применяют», «настраивают», «делают» в значении абстрактных третьих лиц): инструкции пишутся с прямым уважительным обращением к читателю на «вы» («используйте», «вы можете настроить»), либо строятся вокруг самого инструмента («для этого подойдет плагин», «скрипт позволяет автоматически найти»). Конструкции вроде «для этого используют плагин» создают ощущение отстраненного машинного пересказа и отрывают руководство от читателя.
   - Запрещена тавтология первого абзаца с дальнейшим контентом статьи: вводный абзац не должен забегать вперед, пересказывать последующие шаги или преждевременно перечислять форматы, плагины и названия подразделов `<Divider>`, которые раскрываются ниже. Если в статье есть подразделы, вводный абзац формулирует только общую задачу или архитектурную причину, не создавая семантического эха и дублирования с последующим текстом. Читатель не должен читать одно и то же дважды — сначала сжато во вступлении, а затем подробно через две строки.
   - Стандарт первого абзаца по типу вопроса:
     - Вопросы прямого действия («Как включить/отключить», «Где найти», «Куда пропало», «Как настроить»): ноль разгонных преамбул. Сразу прямой ответ: путь в меню, горячая клавиша или первый шаг инструкции.
     - Вопросы причин и теории («Почему...», «Из-за чего...», «Что означает...», «В чём разница...»): органичный компактный контекст (ориентир 1–3 предложения, ~25–45 слов). В сбоях — симптом и условие воспроизведения в реальной работе («Сбой происходит при..., когда...»). В теории и интерфейсе — преодоление типичного заблуждения новичков (почему интуитивное понимание ошибочно).
     - Обзорные вопросы выбора («Какими средствами...», «Как и чем...»): 1–2 предложения контекста о материале и задаче с ПОЛНЫМ ЗАПРЕТОМ на названия программ и плагинов в первом абзаце. Конкретный софт раскрывается строго в подразделах `<Divider>`.
     - Общие требования: естественный связный язык без сухих конспектов и формул, уважительное обращение на «вы», чистый инфостиль без вводных клише.
9. Паттерны сохранения технической матчасти:
   - Критерий проверки ценности: «Если убрать эту фразу, потеряет ли читатель понимание софта?». Пустые разгонные фразы удаляются, но архитектурная физика и принципы работы софта обязательно сохраняются.
   - Паттерн 1 (Механика сразу после прямого тезиса): первый абзац начинается с факта/симптома, а вторым предложением сразу дается физика процесса (причина на уровне архитектуры), без разгонных преамбул.
   - Паттерн 2 (Вынос матчасти в `<Addition type="info">`): быстрое решение дается в основном тексте за 2 секунды, а глубокое объяснение причин или архитектурных нюансов выносится чистым текстом (без шаблонных префиксов) в блок `Addition type="info"`.
   - Паттерн 3 (Архитектурный разбор через `<Divider>`): при объемном теоретическом разборе материал делится на блоки: `<Divider>Как решить проблему</Divider>` и `<Divider>Почему возникает этот сбой</Divider>`.
10. Регламент правок контента:

- Гибридный подход: очевидные клише («В этой статье мы рассмотрим...») удаляются чистовиком сразу. Глубокие концептуальные перестройки вводных абзацев или спорные формулировки помечаются двухстрочным JSX-комментарием непосредственно перед проблемным фрагментом: `{/* REVIEW: <причина замечания>` `    Вариант: <конкретный готовый текст исправления или действие> */}`.
- Запрещено затирать служебные комментарии (`FIXME`, `TODO`, комментарии рефакторинга) и черновики в текущих диффах без прямого указания пользователя.
- Запрещено скрывать статьи целиком или искажать существующие теги без подтверждения пользователя.

11. Специализированные субагенты редакции:
    - `factcheck-editor`: глубокий фактчекинг версий программ, совместимости плагинов, актуальности ссылок и выявление признаков машинной генерации.
    - `proofreader`: вычитка русской грамматики, орфографии, пунктуации, слитного/раздельного написания («в принципе», «во что-то»), согласования падежей («реализация создания») и распутывания синтаксических петель при сохранении живого авторского стиля и технических тегов.
    - `cross-faq-sync`: сопоставление и синхронизация повторяющихся абзацев, инструкций и общих тем между `aefaq`, `prfaq` и `psfaq` (за основу берётся вариант из `aefaq`, либо по последнему коммиту, либо предлагается улучшенный сбалансированный вариант без машинного тона и скобок).
    - `media-density-aligner`: анализ скриншотов высокого разрешения интерфейса и диалоговых окон в статьях с расстановкой пропа `density={1.75}` (или кастомной плотности).
    - Все вердикты и рекомендации субагентов передаются автору для обязательного ручного ревью перед внесением чистовых правок.
12. Межпрограммная синхронизация и модульный каркас:
    - Полная синхронизация: платформенные темы и общие инструкции синхронизируются строго дословно, отличаясь только названиями программ и системными путями.
    - Модульный каркас: если задача общая, но инструменты хостов или версии плагинов различаются, синхронизируется внешний каркас статьи (нейтральный вводный абзац, блоки предупреждений и структура подразделов `<Divider>`), а специфика конкретного софта, интерфейса и медиа раскрывается внутри соответствующих блоков.

## Регламент коммитов

1. Атомарность: один логический блок изменений = один атомарный коммит. Не объединять несвязанные изменения в один коммит.
2. Контроль: не выполнять `git add`, `git commit`, `rebase` и push без отдельного явного запроса пользователя. План коммитов предлагать только по требованию.
3. Безопасность разбиения: для разделения сложных правок использовать временные `.bak`-файлы, не включая их в коммит и удаляя после фиксации.
4. Формат сообщения: `<type>(<scope>): <результат на русском языке>`.
   - Запрещено использовать прямые имена файлов и переменных в сообщении.
   - Заголовок (subject) формулировать в прошедшем времени совершенного вида без точки в конце: `добавлен`, `исправлено`, `обновлены`, `удалены`, `вынесены`.
   - Запрещено использовать флаг `--no-verify`.
   - Основные типы: `content`, `refactor`, `fix`, `feat`, `docs`, `chore`, `style`, `format`.
   - Основные скоупы: `components`, `aefaq`, `styles`, `hooks`, `prfaq`, `docs`, `app`, `psfaq`, `config`, `deps`, `utils`, `scripts`.
   - Правило выбора скоупа: всегда использовать один основной скоуп. Мультископ (перечисление через запятую) допускается преимущественно для одновременных изменений в статьях разных разделов (`aefaq, prfaq, psfaq`).
   - Для точечных исправлений неотправленных коммитов использовать `git commit --fixup <hash>` с последующим интерактивным автосквошем.
5. Перед коммитом выводить `git diff --staged --name-only` и краткую сводку фиксируемых изменений.

Шаблон плана коммита:

- `Файл: <путь>`
- `---`
- `Коммит: <type>(<scope>): <сообщение>`
- `Изменения: <кратко>`

## Итоговый отчет (Definition of Done)

После выполнения задачи предоставить краткий отчет:

1. Список измененных файлов.
2. Что конкретно сделано и почему этого достаточно.
3. Выполненные статические проверки (типы, импорты, синтаксис).
4. Что не проверялось и потенциальные риски.
5. Проводилась ли индексация проекта и с какой целью.
